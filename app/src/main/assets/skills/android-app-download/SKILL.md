# 下载 Android App

## 确认目标

- 从用户需求提取应用名称、开发者、指定版本、发布渠道和设备需求。已有信息足够时直接推进。同名应用会导致选错时，先用发布者和包名消歧。
- 区分下载、安装和查找链接。只要求下载时，交付文件与来源即可。另有安装要求时，按现有安装工具和授权流程执行。

## 找到可信链接

1. 用户未提供可用直链时，调用 `executeResearchTask` 委托 ResearchAgent 做 Web 搜索，再用 `waitResearchTask` 取结果。要求它实际打开官网或官方发布页，核对开发者身份，区分来源页面、应用商店页面和可直接下载的文件 URL。
2. 优先采用开发者官网、官网指向的官方发布仓库或开发者明确推荐的分发渠道。搜索结果排名和文件名不足以证明来源。用户提供直链时，可跳过搜索，但仍应核对来源和文件类型。若地址会跳转，关注最终下载来源是否符合预期。
3. 让 ResearchAgent 记录能确认的版本、发布渠道、包名、最低 Android 版本、ABI、文件尺寸及官方校验值。只在有可靠依据时填这些字段。若用户要求最新版，优先选最新稳定版，除非用户指定测试版。
4. 优先选匹配设备的 APK。无法确定 ABI 时，可选官方明确标注的通用版。AAB 是发布包，单独的 split APK 通常不是完整安装包。遇到 APKS、XAPK、APK 分包或多个 ABI 变体时，保留其实际格式，说明所需安装方式。无法确定适用变体时，再向用户确认。

## 官网内跳转与等待

1. 官网需要点击下载入口、切换平台或展开下载选项时，委托 `executeBrowserTask`，传入已核实的来源页面。委托说明要明确要求等待页面跳转后再查 APK 链接。上层调用 `waitBrowserTask` 取回结果。
2. Browser Use 执行导航或点击可能跳转的链接后，必须在同一 `tabId` 上用 `awaitBrowserEvent(tabId, afterRevision)` 等待。首次使用操作返回的 `revision`，之后用最新事件的 `revision` 继续等。收到 `UrlChanged` 只能确认地址变了，继续等到 `NavigationFinished` 后，再用 `searchBrowserHtml` 查找链接。收到 `NavigationFailed` 时记录错误和当前 URL。
3. 等待超时后用 `listBrowserTabs` 检查当前 URL 和加载状态。仍在加载就继续等待，不采信旧页面。确认只是同页展开或局部更新、没有可等的导航事件时，可调用一次短暂的 `waitBrowserTime`，再从当前页面重新读 HTML 或截图，核对预期内容是否出现。连续无变化时说明卡在哪一步。

## 下载和验证

1. 已有可信直链时，优先用当前可用的直接下载工具。若当前只提供 Linux 下载能力，调用 `executeProotLinuxTask` 下载并用 `exportProotFileToSession` 导出到当前会话，再调用 `waitLinuxTask`。委托时明确给出直链、预期文件名和可用的校验信息。
2. 检查请求结果、文件存在且非空、文件格式与预期相符。下载到 HTML 登录页、验证码页或错误页时按失败处理。发布方提供校验值时比较实际文件的哈希，发现不匹配时停止交付并说明原因。只有在拿到可信签名指纹并完成比对时，才报告签名已验证。
3. 确认导出结果包含会话附件 ID，交付时提供文件名、来源页面、已确认的版本和架构，以及校验状态。工具返回任务 ID 或下载路径时，还要等待实际结果并确认会话中已能访问产物。

## 无法取得 APK 时

- 只找到官方商店页面时，提供该页面并说明没有找到公开直链。不要猜测下载 URL，也不要默认选择不明镜像。
- 如果目标要求登录、用户授权或只能在商店完成，说明具体条件。只有用户要求通过该界面继续、且确实没有直接途径时，才考虑委托 DeviceActionAgent 进行必要的界面操作。
